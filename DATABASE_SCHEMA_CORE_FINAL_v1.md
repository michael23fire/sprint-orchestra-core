## Database Tables

### Table: users

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| id | BIGINT | PK, identity | User id |
| username | VARCHAR(50) | UNIQUE, NOT NULL | Login username |
| name | VARCHAR(100) | NOT NULL | Display name |
| email | VARCHAR(150) | UNIQUE, NOT NULL | User email |
| password | VARCHAR(100) | NULL | Password hash / auth field |
| avatar_color | VARCHAR(100) | NULL | UI avatar color |
| created_at | TIMESTAMPTZ(6) | NOT NULL | Created time |
| updated_at | TIMESTAMPTZ(6) | NOT NULL | Updated time |

**Indexes / Constraints:**
- `PRIMARY KEY (id)`
- `UNIQUE (username)`
- `UNIQUE (email)`

**SQL:**

```sql
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(150) NOT NULL,
    password VARCHAR(100),
    avatar_color VARCHAR(100),
    created_at TIMESTAMP(6) WITH TIME ZONE NOT NULL,
    updated_at TIMESTAMP(6) WITH TIME ZONE NOT NULL,
    CONSTRAINT uk_users_username UNIQUE (username),
    CONSTRAINT uk_users_email UNIQUE (email)
);
```

### Table: spaces

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| id | BIGINT | PK, identity | Space id |
| name | VARCHAR(100) | NOT NULL | Space name |
| space_key | VARCHAR(20) | NOT NULL (active unique index) | Space key |
| color | VARCHAR(30) | NULL | Space color |
| owner_id | BIGINT | FK -> users(id), NULL | Owner user id |
| issue_counter | INTEGER | NOT NULL | Incremental issue counter per space |
| created_at | TIMESTAMPTZ(6) | NOT NULL | Created time |
| updated_at | TIMESTAMPTZ(6) | NOT NULL | Updated time |
| github_pat | TEXT | NULL | Optional per-space GitHub PAT (V8) |
| deleted_at | TIMESTAMPTZ(6) | NULL | Soft-delete timestamp (V10) |

**Indexes / Constraints:**
- `PRIMARY KEY (id)`
- `UNIQUE INDEX uk_spaces_space_key_active (space_key) WHERE deleted_at IS NULL`
- `FOREIGN KEY (owner_id) REFERENCES users(id)`
- `idx_spaces_deleted_at (deleted_at)`

**SQL (V1 + V8 + V10):**

```sql
CREATE TABLE spaces (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    space_key VARCHAR(20) NOT NULL,
    color VARCHAR(30),
    owner_id BIGINT,
    issue_counter INTEGER NOT NULL,
    created_at TIMESTAMP(6) WITH TIME ZONE NOT NULL,
    updated_at TIMESTAMP(6) WITH TIME ZONE NOT NULL,
    CONSTRAINT uk_spaces_space_key UNIQUE (space_key),
    CONSTRAINT fk_spaces_owner FOREIGN KEY (owner_id) REFERENCES users (id)
);

ALTER TABLE spaces ADD COLUMN github_pat TEXT NULL;

ALTER TABLE spaces
    ADD COLUMN deleted_at TIMESTAMP(6) WITH TIME ZONE NULL;

CREATE INDEX idx_spaces_deleted_at ON spaces (deleted_at);

ALTER TABLE spaces DROP CONSTRAINT uk_spaces_space_key;

CREATE UNIQUE INDEX uk_spaces_space_key_active ON spaces (space_key) WHERE deleted_at IS NULL;
```

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| id | BIGINT | PK, identity | Attachment id |
| issue_id | BIGINT | FK -> issues(id), NOT NULL | Issue id |
| uploader_id | BIGINT | FK -> users(id), NULL | Uploader |
| original_filename | VARCHAR(255) | NOT NULL | User filename |
| storage_filename | VARCHAR(255) | UNIQUE, NOT NULL | Stored filename |
| content_type | VARCHAR(120) | NULL | MIME type |

| created_at | TIMESTAMPTZ(6) | NOT NULL | Upload time |

**Deletes:** Removing a row (via the attachments API) deletes metadata here and the corresponding object in app storage. Rich-text fields on **`issues`** / **`comments`** may still mention the same attachment id or filename until updated by the application — there is **no** DB trigger to scrub HTML.

**SQL (V4 + V7):**

```sql

    CONSTRAINT fk_issue_attachments_uploader FOREIGN KEY (uploader_id) REFERENCES users (id),
    CONSTRAINT uk_issue_attachments_storage_filename UNIQUE (storage_filename)
```

## Key Relationships

### Relationship 1: Space-centered hierarchy

- `spaces` -> `sprints` (1:N)
- `spaces` -> `issues` (1:N)
- `issues` -> `comments` / `work_logs` / `issue_history` / `issue_attachments` / `issue_code_links` (1:N)

This is the core work-management domain path.

### Relationship 2: Membership model

- `spaces` <-> `users` via `space_members`
- `user_groups` <-> `users` via `group_members`
- `spaces` <-> `user_groups` via `space_groups`

This supports both direct and group-based membership assignment.

### Relationship 3: Issue graph model

- `issues.parent_id` supports parent-subtask hierarchy
- `issue_links` supports arbitrary typed links across issues

Used for dependency graph and cross-ticket traceability.

### Relationship 4: Dev integration model

- `space_github_repos` defines allowed repos per space
- `issue_code_links` stores issue-level links to PRs/commits/repos
- `spaces.github_pat` enables per-space private repo access workflows

## Notes on Implementation

1. **Schema ownership**
   - Schema is managed by Flyway migrations (`V1`..`V10`)
   - JPA is configured with validation mode (`ddl-auto: validate`)

2. **Issue identifiers**
   - `issues.id` is relational primary key
   - `issues.issue_key` is unique business key exposed in UI/API

3. **Rich content storage**
   - `issues.description` and `comments.content` are `TEXT` and may contain HTML/rich editor output

4. **Attachment model**
   - Physical file storage references via `storage_filename`
   - `list_in_attachment_panel` allows UI visibility control for embedded attachments
   - Deleting an `issue_attachments` row does **not** automatically clean HTML references inside `issues.description` / `comments.content` (application responsibility)

5. **GitHub integration**
   - `space_github_repos` and `issue_code_links` are first-class core tables in current project
   - `last_activity_at` supports activity-based ordering and freshness in UI

6. **Index strategy**
   - Foreign key columns for high-frequency lookups are indexed
   - Unique constraints enforce domain invariants (space key, issue key, membership uniqueness, repo uniqueness)

7. **Deletion behavior**
   - Most FKs use default PostgreSQL behavior (restrict if referenced)
   - No broad cascade chains are defined in current schema; deletes should be orchestrated by service logic
   - `spaces` uses soft-delete semantics via `deleted_at` with active-row uniqueness on `space_key`
